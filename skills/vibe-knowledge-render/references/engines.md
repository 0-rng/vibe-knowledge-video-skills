# Canvas、Remotion 与同一时间轴

## 固定动画管线

按事件表现需求选择画面方法。Canvas + JavaScript是已有优先路线，复杂材质可用WebGL；也可用SVG形变、分层插画/2.5D、合格人物或道具、图像序列和角色动画。不得因单一技术把关键动作降级成长文字、静图推拉或简单光球。工程内锁定的Remotion统一帧号、字幕、声音、合成与正式导出，本机Chrome执行。已有素材和动作方法可直接纳入同一时间轴，不为强制迁移到Canvas而损坏事件与造型。

Canvas 是允许且优先的主体绘制方式，不能将旧规则中的“禁止独立捕获管线”误读成禁止 Canvas。其帧绘制由 Remotion 驱动；不另建 HyperFrames、Playwright 截图编码、自写 Python 视频帧生成器或屏幕录制路线。CSS/SVG 和图像分层仍可在 Remotion 中负责适合的内容，不建立第二套时钟。FFmpeg 可继续承担既有音频处理和媒体检查；其使用不改变声音流程。

## 本机 Chrome 与版本

- 先确认本机 Chrome 的可执行文件存在。在当前 macOS 环境中，已验证路径是 `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`；其他机器按实际安装位置确认，不能照搬失效路径。
- 在正式 still / render 命令中显式传入 `--browser-executable`，或在 Renderer API 的 `browserExecutable` 中指定同一路径；不要仅依赖可能被改动的隐式配置，也不要进入自动下载浏览器的流程。
- 使用工程内安装并锁定的 Remotion 版本，以本地类型和实现核实 API、CLI 选项；不要通过不确定版本的 npx 临时拉取最新版。不要照抄不存在的配置 API 或未经核实的浏览器参数。
- Chrome 启动失败时区分浏览器故障与 TypeScript／组件错误，检查路径、运行权限、版本和启动日志。需要沙箱外运行时使用正常权限流程；无法继续时说明具体缺口，不以换引擎或下载其他浏览器替代排查。

## 组件与帧驱动动画

- React/TypeScript组织场景，按事件选Canvas、SVG、分层素材、角色/图像序列或WebGL；素材方法必须保留可观察行为，不能仅作静态推拉。Canvas细节见 [绘制与材质](canvas-animation.md)。确需模型才评估ThreeCanvas，不把WebGL与Three.js混为一谈。
- 由 `useCurrentFrame()` 和工程 fps 推导时间；`interpolate()` 控制位置、透明度、角度及数值，`spring()` 控制需要弹性的动作。动画不可依赖自由运行的 CSS transition／keyframes、墙钟、setInterval、requestAnimationFrame 或未经确定性重放的累积状态。
- 使用 `Sequence` 明确场景起点和持续帧数，让场景内部读取局部时间。不要混用全片帧号与局部帧号，避免后续场景跳过入场或结尾尚未出现就被截断。
- 动作开始、移动、接触、反应和停留分别安排；优先让字幕语义与动作节点对应。复用旧镜头时可以映射时间，但不要把整段统一拉伸作为常规做法，导致入场迟缓或关键动作速度失真。
- 固定随机种子，任意目标帧都能独立求值；顺序、乱序和重复渲染的同一帧应一致。粒子直接按出生时间、初速度与年龄求值；需要状态积分时从固定初态或检查点重放至目标帧，不依赖上一截图残留的状态。接触对象和连线共享几何关系，避免脱离、穿透或受力方向矛盾。

## 时间轴与正式导出

以已确认的观看轨、事件分镜、必要文字阅读和音乐段落安排动作，不从知识轨全文生成字幕时间轴。没有旁白时不创建 TTS 或虚构旁白轨，也不把生成旁白作为动画渲染前置步骤；用户提供其他已确认时间依据时沿用。

分镜、字幕、动作事件和已有声音事件共用一个时间原点，预览与导出共用状态计算。等待字体、图像和其他素材实际就绪，并完成目标帧绘制、素材解码及所用图形管线提交后才捕获，不能仅等固定秒数。通过 `delayRender`/`continueRender` 将就绪状态与捕获关联；Canvas/WebGL 细节按专门参考处理。

先用 Remotion 的正式 `still` 检查关键帧，再用正式 `render` 导出能暴露风险的连续样段，修正后继续全片。已有的造型、动作、声音与媒体验收标准保持适用；渲染成功不等于美术与动作通过。

使用 Remotion 支持的帧区间或分段能力验证局部修改，按实际资源选择并发度，不为每条片重新编写截图循环或独立编码流程。

官方依据：[核心原理](https://www.remotion.dev/docs/idea)、[Sequence](https://www.remotion.dev/docs/sequence)、[确定性与闪烁](https://www.remotion.dev/docs/flickering)、[ThreeCanvas](https://www.remotion.dev/docs/three-canvas)、[render](https://www.remotion.dev/docs/cli/render)。其他参考资料中的旧引擎做法仅供比较，不覆盖本文件的 Remotion 与本机 Chrome 要求。

## 时间、性能和停止

分镜、字幕、物件与音效共用原点。音频采样换算与帧时间一致；瞬态落点参照真实动作，而非文件开头。

已有规格优先；本系列按STYLE_BIBLE固定1080p/30fps；用户明确变更为60fps时才逐帧重新计算，不用重复帧凑帧率。画幅按发布场景构图。先在目标配置下做短样段测量速度和资源。如果硬件支持可核实的 GPU 路径，先验证再使用；不要无理由强制软件渲染整片。也不能只验证GPU存在就声称画质和速度已经提高。

明确任务所属进程，支持失败与用户停止时回收浏览器、编码器和工作进程，不影响其他用户应用。渲染中保持进展可见，不以长时间无反馈的后台任务代替交付。

帧区间采用明确的半开区间约定，例如 N 帧覆盖 frame 0…N−1；不要从别的项目抄一个“时长×fps＋1”当通用正确值。媒体验收以实际帧数、PTS、音频时长和尾帧为依据。
